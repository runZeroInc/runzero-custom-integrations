# Custom Integration: Foreman

## runZero requirements

- Superuser access to the [Custom Integrations configuration](https://console.runzero.com/custom-integrations) in runZero.

## Foreman requirements

- Foreman 3.x or later with the REST API v2 enabled. The API is always on; there is no
  setting to turn it off.
- A Foreman user with a role granting `view_hosts` and `view_facts`. A read-only role is
  sufficient; the integration never writes.
- That user must be assigned to every **organization** and **location** whose hosts should
  be imported, or be an administrator. Foreman filters both the host list and the fact
  values by the user's taxonomies, so an unassigned organization is invisible rather than
  an error.
- Either a **Personal Access Token** for that user (preferred) or the user's password.
- On Katello, Red Hat Satellite, or orcharhino, the same user also needs read access to
  content hosts if the Katello package inventory is going to be imported.
- Foreman installs almost always present a self-signed certificate generated by the
  installer. Either add that CA to the Explorer's trust store or set the integration's
  TLS option `disable_validation`.

## Steps

### Foreman configuration

1. Sign in to Foreman and go to **Administer > Users**. Create or pick the user the
   integration will run as.
2. Go to **Administer > Roles** and either assign an existing read-only role or create one
   with the `view_hosts` and `view_facts` permissions, then assign it to that user on the
   **Roles** tab of the user.
3. On the user's **Locations** and **Organizations** tabs, add every taxonomy whose hosts
   should be imported.
4. Open the user again and go to the **Personal Access Tokens** tab. Click
   **Add Personal Access Token**, give it a name and an optional expiry, and copy the
   generated token. Foreman displays it exactly once. Use the token in place of the
   password; Foreman accepts it anywhere a password is accepted, in the UI and the API
   alike.

### runZero configuration

1. [Create the Custom Integration](https://console.runzero.com/custom-integrations/new).
   - Add a Name and Icon for the integration (e.g., "Foreman").
   - Toggle `Enable custom integration script` to input the finalized script.
   - Click `Validate` to ensure it has valid syntax.
   - Click `Save` to create the Custom Integration.
   - The script embeds its `CONFIG` block, so the credential form is generated automatically with the fields below.
2. [Create the Credential for the Custom Integration](https://console.runzero.com/credentials).
   - Select the type `Custom Integration Script Secrets`.
   - **Foreman URL** (`url`): base URL of the Foreman server, for example `https://foreman.example.com`. The `/api/v2` path is appended automatically.
   - **Username** (`username`): the Foreman user the integration authenticates as.
   - **Password or Personal Access Token** (`password`): that user's Personal Access Token, or its password.
   - **Host search filter** (`search`): optional; a Foreman search query applied to the host list, for example `managed = true`.
   - **Import Facter facts** (`include_facts`): optional; fetch hardware, OS, and per-interface facts in bulk (default: true).
   - **Fetch the interface list per host** (`include_interfaces`): optional; one extra request per host for Foreman's own interface records (default: false).
   - **Import Katello package inventory** (`include_packages`): optional; one extra request per host, skipped automatically on plain Foreman (default: false).
   - **Per-host request limit** (`detail_limit`): optional; cap on how many hosts get the per-host requests (default: 1000, 0 removes the cap).
   - **Hosts per page** (`page_size`): optional; hosts requested per page (default: 100).
   - **Fact values per page** (`fact_page_size`): optional; fact values requested per page (default: 1000).
   - **Additional fact names** (`extra_facts`): optional; comma-separated Foreman fact names to import alongside the built-in set. A name containing a double quote cannot be placed in the scoped-search string and is ignored with a log line, so one typo cannot 400 the whole fact walk.
3. [Create the Custom Integration task](https://console.runzero.com/ingest/custom/).
   - Select the Credential and Custom Integration created in steps 1 and 2.
   - Update the task schedule to recur at the desired timeframes.
   - Select the Explorer you would like the Custom Integration to run from.
   - Click `Save` to kick off the first task.

### Running it from the command line

The runZero Explorer binary runs a script directly, which is the fastest way to
confirm a token and see what a real Foreman returns before scheduling anything.
`--kwargs` is repeated once per parameter:

```bash
runzero script --filename foreman/foreman.star \
  --kwargs url=https://foreman.example.com \
  --kwargs username=runzero \
  --kwargs password=1a2b3c4d5e6f70819a0b1c2d3e4f5061 \
  --kwargs include_facts=true \
  --kwargs page_size=25 \
  --kwargs detail_limit=10 \
  --custom-integration-id 1f2e3d4c-5b6a-7988-9a0b-1c2d3e4f5a6b \
  --output ./foreman-run
```

`--output` writes the assets the run produced, and `--overwrite` replaces a
directory from a previous run — the scanner refuses an `--output` directory that
already exists otherwise. Add `--verbose` for the request-by-request log. Omit
`--output` to see only the log lines.

The `password` parameter takes a Personal Access Token exactly as it takes a
password, so the example above is a token. Keep `detail_limit` low while
testing: `include_interfaces` and `include_packages` are one extra request per
host each, and on a few thousand hosts that dominates the run.

Because the installer's self-signed certificate is the normal case, a first run
that fails on TLS rather than on authentication usually needs the CA rather
than a different URL:

```bash
runzero script --filename foreman/foreman.star \
  --kwargs url=https://foreman.example.com \
  --kwargs username=runzero \
  --kwargs password=1a2b3c4d5e6f70819a0b1c2d3e4f5061 \
  --kwargs tls_ca_cert=/etc/foreman/proxy_ca.pem \
  --custom-integration-id 1f2e3d4c-5b6a-7988-9a0b-1c2d3e4f5a6b \
  --output ./foreman-tls --overwrite
```

**One parameter here needs care on the command line, and it is not the obvious
one.** `--kwargs` passes a value through verbatim, commas included, as long as
the pair contains a single `=`; only a value carrying a *second* `=` **as well
as** a comma is re-read as CSV. So:

- **`extra_facts`** is comma-separated by definition, and that is fine — no fact
  name contains an `=`, so
  `--kwargs extra_facts=ansible_processor_count,rhsm::role` arrives as the
  two-name list you wrote.
- **`search`** is the one to watch. A Foreman query such as
  `organization = Acme, location = HQ` carries both an `=` and a comma, so it is
  split: `search` ends up holding `organization = Acme` alone, and a second,
  fabricated parameter appears named after the rest — silently, with no error.
  Wrap the whole argument in double quotes so it stays a single CSV field,
  `--kwargs '"search=organization = Acme, location = HQ"'`, doubling any double
  quote inside the query. Single-term searches need nothing special.

To check the `CONFIG` block and the HTTP and TLS wiring without a live server:

```bash
runzero script --filename foreman/foreman.star --validate
```

Validation generates placeholder parameter values and answers from a local
dummy server, so it proves the script initializes, declares its parameters
correctly, and issues a request. It does not prove Foreman accepts the
credential, that the user's taxonomies expose any host, or that any host is
parsed.

The fixtures under `foreman/tests/fixtures/` exercise the parsing offline,
including the paging, detail-cap, and missing-Katello cases:

```bash
python3 tests/run.py foreman
```

The same script also runs under the `scan` command, which is what the platform
itself invokes for a scheduled task:

```bash
runzero scan --custom-integration-script-source "$(cat foreman/foreman.star)" \
  --custom-integration-id <uuid-from-the-console> \
  --custom-integration-script-kwargs 'url=https://foreman.example.com,username=runzero,password=<token>' \
  --output ./foreman-scan
```

`--custom-integration-id` is the UUID the console shows on the integration's
page. `--custom-integration-entry-function-name` defaults to `main`. Note that
`--custom-integration-script-kwargs` is the genuinely strict one: it takes a
single comma-separated string, so no value passed through it may contain a comma
at all — `extra_facts` and a multi-term `search` are both unusable there, even
though `script --kwargs` handles them.

### What's next?

- You will see the task kick off on the [tasks](https://console.runzero.com/tasks) page like any other integration.
- The task will update existing assets with data pulled from Foreman.
- The task will create new assets when there are no existing assets that meet merge criteria (hostname, MAC, etc).
- You can search for assets enriched by this custom integration with the runZero search `custom_integration:foreman`.

## Asset identity

- Target entity: a host managed or recorded by Foreman — a provisioned bare-metal server,
  a VM on a registered compute resource, or an unmanaged record created by a fact upload.
- Source ID field: `id` on the host record returned by `GET /api/v2/hosts`.
- Documentation evidence: the [hosts index](https://apidocs.theforeman.org/foreman/3.16/apidoc/v2/hosts/index.html)
  returns `{"total", "subtotal", "page", "per_page", "search", "sort", "results": [{"id", "name", ...}]}`,
  and every per-host route is keyed on it — `GET /api/v2/hosts/:id`,
  `GET /api/v2/hosts/:host_id/facts`, `GET /api/v2/hosts/:host_id/interfaces`. In the
  source, `id` is the Rails primary key of the `hosts` table; `organization_id` and
  `location_id` are ordinary columns on that same row, not part of the key.
- Uniqueness scope: one Foreman instance. Foreman's multi-organization and multi-location
  model does **not** widen the scope: taxonomies partition *visibility*, not the id
  sequence, and moving a host between organizations keeps its id. This is the opposite of
  the Quest KACE appliance, where each organization is a separate database and the machine
  id has to carry the organization to stay unique — for Foreman, adding the organization
  would be actively wrong, because a host that is moved between organizations would then
  be renumbered into a second runZero asset.
- Cardinality: one row per asset. Interfaces, facts, packages, and reports are child rows
  of that host and are folded into the same asset rather than becoming assets of their own.
- Stability: survives rename, reboot, IP and MAC change, fact re-upload, organization and
  location moves, hostgroup changes, and a full rebuild through Foreman — a host put back
  into build mode and reprovisioned keeps its record and therefore its id. It is replaced
  only when the host is deleted from Foreman and created again, which produces a genuinely
  new record.
- Reuse behavior: `id` comes from a PostgreSQL sequence backing a Rails primary key, which
  does not reissue values for deleted rows while the table exists. A database restore from
  a dump taken before a host existed could in principle reissue a value; this is the same
  exposure every self-hosted autoincrement id carries.
- Presence: always present, on both the list and the detail response. It is the field the
  API routes on. `thin=true` reduces the response to `id` and `name` and nothing less.
- Final runZero ID: `foreman:<foreman-host>:<id>`, for example
  `foreman:foreman.example.com:2481`. The host comes from the configured URL, so two
  Foreman servers imported into one runZero account cannot collide.
- Missing-ID behavior: the record is skipped and one line is logged with the host name
  only. No identity is synthesized and `new_uuid()` is never used.
- Match behavior (set once in `CONFIG`): `no-mac-break no-ip-break no-name-break`. The id is authoritative, but
  Foreman holds exactly one `ip`, one `ip6`, and one `mac` on the host record and rewrites
  all three from DHCP and from every fact upload, and hosts are renamed in place. A
  deleted-and-recreated host also arrives with a new id and must still merge onto the
  existing runZero asset by hostname or MAC.
- Verdict: scoped authoritative — authoritative within one Foreman instance, namespaced by
  the instance host.

### Why not `name` or `certname`

`name` is the FQDN and Foreman validates it for uniqueness across the whole instance, so
it is a *candidate* key. It was rejected on two counts. Hosts are renamed in place, which
would fragment one machine into two assets. More seriously, a decommissioned host that is
deleted and a new unrelated host built with the same FQDN would fuse into one asset,
carrying the old machine's serial number and hardware forward — exactly the failure the
`id` avoids.

`certname` is worse: it defaults to `name`, but when the Foreman setting
`use_uuid_for_certificates` is enabled Foreman assigns `Foreman.uuid` — a **random UUID**
generated per record. An identity that is sometimes the FQDN and sometimes a random value,
depending on a server-side setting, is not usable. Both fields are still imported: `name`
and `certname` become hostnames so runZero can merge on them.

### Notes

- **What is imported.** Assets from `GET /api/v2/hosts`. Facter facts from one paged pass
  over `GET /api/v2/fact_values`. Network interfaces from those facts, from the host
  record's own `ip`/`ip6`/`mac`, and — behind `include_interfaces` — from the `interfaces`
  array on `GET /api/v2/hosts/{id}`. Installed packages, behind `include_packages`, from
  Katello's `GET /api/v2/hosts/{id}/packages`. Every mapped field is also kept verbatim as
  a `foreman_*` custom attribute.
- **The N+1 was avoided, and this was the central design decision.**
  `GET /api/v2/fact_values` returns facts for **every** host the user can see in one paged
  call — `results` is an object keyed by host name whose values are flat
  `{fact_name: value}` maps — so no per-host fact request is needed. The catch is real and
  had to be designed around: Foreman applies pagination to the *fact value* rows before
  grouping them by host (`FactValue…paginate(paginate_options)…pluck(:value, 'fact_names.name', 'hosts.name')`
  in `app/controllers/api/v2/fact_values_controller.rb`), so **`per_page` counts individual
  facts, not hosts, and one host's facts routinely straddle a page boundary**. Treating
  each page as a complete fact set for the hosts it names would silently drop facts. The
  integration merges pages into a single map keyed by host name instead, which also makes
  the endpoint's ordering irrelevant. Verified against fixtures: the same estate read at
  `fact_page_size=7` and at `fact_page_size=10000` produced byte-identical assets.
- **The fact walk is filtered, not exhaustive.** A Facter 4 host reports several hundred
  facts, and Foreman additionally stores a null-valued row for every composite parent of a
  nested fact, so an unfiltered walk would read the entire fact table. The integration
  sends a `search` naming the facts it actually maps (`fact = "dmi::product::serial_number" or …`)
  plus one prefix term (`fact ~ "networking::interfaces::"`) for the per-interface facts,
  whose names contain the device name and so cannot be listed. That prefix term does return
  every per-interface fact, including ones that are not mapped (`mtu`, `netmask`,
  `bindings`), which is the main driver of the row count. Budget roughly 40 fact rows per
  host plus about 13 per interface. `extra_facts` appends further exact fact names.
- **Fact names use `::`, not `.`.** Foreman flattens a structured fact tree with
  `FactName::SEPARATOR`, which is `'::'`, so Facter's `dmi.product.serial_number` is stored
  as `dmi::product::serial_number` and `networking.interfaces.eth0.mac` as
  `networking::interfaces::eth0::mac`. Composite parents such as `networking::interfaces::eth0`
  exist as rows with a null value and are skipped.
- **Both the structured and the legacy flat fact names are requested.** Which set a host
  reports depends on the agent: Facter 4 through Puppet writes `dmi::product::serial_number`
  and `os::release::full`, older agents write `serialnumber` and `operatingsystemrelease`.
  Every mapping tries the structured name first and falls back to the flat one.
- **Facts from Ansible, Salt, and subscription-manager are not mapped.** Foreman accepts
  facts from any of them and stores them in the same table, but under entirely different
  names (`ansible_default_ipv4::address`, `network::interfaces::…`). Hosts inventoried only
  by those tools still import, with the host record's own address and no hardware facts.
  Their fact names can be added through `extra_facts`, which will surface them as custom
  attributes, though not as interfaces.
- **Pagination.** Every v2 index action answers with the same envelope — `total`,
  `subtotal`, `page`, `per_page`, `search`, `sort`, `results` — with the root node fixed to
  `results` (`json_root_default_name = :results` in `config/initializers/rabl_init.rb`).
  Paging is 1-based and advances until a short or empty page arrives. `subtotal` is
  deliberately not trusted as a stop condition: on a searched request Foreman computes it
  as `@fact_values.count`, and because that variable is the grouped hash rather than the
  relation, it reports the number of *hosts on the current page*.
- **Interfaces need a decision, and the default is the cheap one.** Foreman returns the
  `interfaces` array only on the single-host response (`app/views/api/v2/hosts/show.json.rabl`
  adds it; the index does not), and there is no top-level `GET /api/v2/interfaces` at all —
  the route exists only nested under a host, domain, or subnet. So per-NIC data is either
  an N+1 or comes from the facts. The default is the facts. `include_interfaces` turns on
  the per-host request, which additionally yields bonds, VLAN devices, subnet names, and
  the `primary`/`managed`/`virtual` flags; it is capped by `detail_limit`.
- **One interface per device, with MACs folded.** A bond and its slaves, and a VLAN device
  and its parent, all report the same MAC. Those are merged into a single runZero interface
  carrying all of their addresses, and the device names are recorded joined with `+` in
  `foreman_interface_identifiers` (for example `bond0+eno1`). The host record's own address
  and MAC are added last, and only when the facts did not already account for them, so a
  host with no facts at all still gets one interface.
- **Loopback is filtered.** `lo` is dropped by device name, and `127.0.0.0/8`,
  `169.254.0.0/16`, `0.0.0.0`, `::1`, `::`, and `fe80::/10` are removed from every address
  list. An all-zero MAC is treated as absent. A host whose only address is `127.0.0.1` is
  imported with **no** network interface rather than sharing an address with every other
  such host, which would merge the estate onto one asset. Its raw values stay in the
  `foreman_ip`, `foreman_ip6`, and `foreman_mac` attributes.
- **BMC interfaces are excluded.** A Foreman interface of type `bmc`, and the host's
  `sp_ip`/`sp_mac`/`sp_name` service-processor fields, describe a separate network endpoint
  with its own address and MAC. Attaching them to the server would make runZero merge the
  BMC's own asset into the server it manages. They are kept as custom attributes only.
- **Timestamps.** Rails serializes these as `2026-08-15T03:10:44.000Z`, always with an
  offset, but the shape is validated before `parse_time` sees it because a value without
  one aborts the whole script. `created_at` becomes `firstSeenTS`. `last_report` becomes
  `lastSeenTS`, and the `0001-01-01T00:00:00.000Z` sentinel is discarded. **A host with no
  configuration-management reports gets no `lastSeenTS` at all.** `updated_at` is
  deliberately not used as a fallback: it moves whenever anybody edits the record in the
  UI and would overstate when the host was last observed.
- **OS comes from the facts first.** `operatingsystem_name` is the *provisioning* record
  and still names the OS the host was built with after an in-place upgrade, so `os::name`
  and `os::release::full` win when present. Without facts, `operatingsystem_name` is split
  at the first dotted numeric token, which matches how Foreman builds it
  (`"<name> <major>.<minor>"`, e.g. `RedHat 9.4`).
- **Katello is opportunistic.** `GET /api/v2/hosts/{id}/packages` is added by Katello
  (`resources :packages, controller: :host_packages` nested under `hosts` in Katello's
  `config/routes/overrides.rb`), so Red Hat Satellite and orcharhino serve it and plain
  Foreman answers 404. That 404 is treated as the absence of a package inventory, not a
  failure: it is logged once and the feature switches itself off for the rest of the run.
  A 403 does the same. When Katello *is* present, `content_facet_attributes` and
  `subscription_facet_attributes` also ride along on the host list for free — Katello
  registers them as facet *list* views, not only single views — so the content view,
  lifecycle environment, content source, applicable and upgradable package counts, the
  per-type errata counts, and the registration and last-checkin times are imported at no
  extra request cost even when `include_packages` is off. Note that the content view and
  lifecycle environment are nested objects on that facet (`content_view.name`), not the
  flat `*_name` fields the rest of the host record uses.
- **Package versions are parsed, not published.** Katello's package API returns only
  `name`, `nvra`, and `nvrea` — there is no separate version, release, or architecture
  field. `bash-5.1.8-9.el9.x86_64` is split into `version=5.1.8`, `update=9.el9`, and
  `targetHardware=x86_64`. `cpe23` is deliberately never set: Katello publishes no CPE, and
  `Software.cpe23` only accepts the CPE 2.2 `cpe:/a:` application binding. Debian hosts on
  Katello report through a different endpoint (`/api/v2/hosts/{id}/debs`) which is not read;
  those hosts import without software. Packages are capped at 99 per asset.
- **No services and no vulnerabilities.** Foreman models neither. It has no listening-port
  inventory of any kind, and no vulnerability object — Katello errata are patch advisories,
  not CVE findings, and are deliberately left out rather than mapped onto `Vulnerability`
  (see Future). Nothing is synthesized for either.
- **Rate limiting.** Foreman publishes no rate limit and returns no `X-RateLimit` headers.
  Transient statuses (408, 425, 429, 5xx) are retried with exponential backoff by the
  shared HTTP helper, which honors `Retry-After`.
- **Degradation.** A failure of the fact walk logs one line and the run continues, importing
  hosts without facts. A failure of one host's detail or package request logs one line and
  that host imports without them. Only a failure of the host list itself ends the run.
- **Unverified assumptions.** The Katello package response shape was read from Katello's
  `host_packages/base.json.rabl` (`id`, `name`, `nvrea`, `nvra`, `upgradable_versions`,
  `rpm_id`, `persistence`) rather than observed. The `~` operator on the `fact` search field
  is documented by Foreman's scoped-search and compiles to a SQL `LIKE`, but the exact
  behavior of a ~60-term `or` query against a large fact table has not been measured on a
  real server; if that query is ever rejected, the run degrades to importing hosts without
  facts rather than failing.
- **This integration was validated against local fixtures, not a live Foreman server.**
  Standing one up was attempted and failed for a reason worth recording: the Foreman
  project's own container images (`quay.io/foreman/foreman:5.0` and `:nightly`, the only
  tags published) ship a glibc built for the **x86-64-v3** microarchitecture level, and
  every binary in the image — including `/bin/echo` and the dynamic loader itself — dies
  with `Fatal glibc error: CPU does not support x86-64-v3` under emulation on Apple
  Silicon. Rosetta does not help: a CPUID probe run under Rosetta reports
  `avx2=0 bmi1=0 bmi2=0 fma=0`. The fixtures were therefore built from the Foreman source
  itself — the controllers, rabl views, models, and routes cited throughout these notes —
  rather than from guessed response shapes.

## Future

- **Outbound: push runZero-discovered hosts into Foreman.** Foreman exposes full host CRUD:
  `POST /api/v2/hosts` with `{"host": {"name", "managed": false, "ip", "mac", ...}}` creates
  a record, `PUT /api/v2/hosts/:id` updates one, and `POST /api/v2/hosts/facts` uploads a
  fact set for a host, creating it if it does not exist. That makes it technically
  straightforward to publish runZero's view of the estate — the OT gear, appliances, and
  unmanaged laptops Foreman has no agent on — back into Foreman as unmanaged host records.
  **The risk deserves stating plainly.** Foreman is a *provisioning system of record*: a
  host record is what decides whether a machine gets rebuilt, what DHCP reservation and DNS
  record a smart proxy publishes, and what kickstart it is served. Writing into it is not
  like writing into an ITAM database. Any outbound integration should create records with
  `managed: false` in a dedicated organization and hostgroup, must never set `build`, must
  never touch an existing managed host, and needs a dry-run mode. The fact-upload route is
  the safer of the two, because Foreman treats fact-created hosts as unmanaged by
  construction.
- **Provisioning and build state as a lifecycle signal.** `build`, `global_status`,
  `configuration_status`, `installed_at`, and `initiated_at` are already imported as
  attributes, but they describe a *lifecycle* runZero has no other view of: a host sitting
  in build mode is about to be wiped and rebuilt, and a host whose `global_status` is Error
  has not reported successfully. A future revision could fold these into a scan-relevant
  signal — for example, suppressing change alerts for a host that Foreman says is mid-build,
  which is otherwise indistinguishable from a machine that has been compromised and
  re-imaged.
- **Katello subscription and errata data as separate classes.** Katello's
  `GET /api/v2/hosts/:id/errata` returns applicable and installable errata with
  `errata_id` (`RHSA-2026:1234`), `type` (`security`/`bugfix`/`enhancement`), `severity`,
  `solution`, `reboot_suggested`, and a `cves` array of `{cve_id, href}`. These are
  **patch advisories, not vulnerability findings**: an erratum says a vendor shipped a fix,
  not that this host is exploitable, and one erratum can bundle a dozen unrelated CVEs. If
  they are ever mapped they should go in as `Vulnerability` records with `category="patch"`
  and the erratum id as the name, with the CVE list as a custom attribute rather than in
  `cve` — mapping one erratum to many CVE findings would multiply an estate's finding count
  by an order of magnitude for no gain in accuracy, and would misrepresent "a patch is
  available" as "this host is vulnerable". The cheap half of this is already done: the
  per-host `errata_counts` on the content facet are imported today as
  `foreman_errata_security`, `foreman_errata_bugfix`, `foreman_errata_enhancement`, and
  `foreman_errata_total`, which answers "which hosts are behind on security errata" without
  inventing findings, and costs no extra request. Subscription state
  (`GET /api/v2/hosts/:id/subscriptions`, `subscription_facet_attributes`) is a third,
  genuinely separate class — entitlement and compliance rather than security — and belongs
  in its own integration if it is wanted at all.
- **Smart proxy DHCP and DNS as an additional network source.** Foreman's smart proxies
  expose `GET /dhcp/:subnet` (every lease and reservation on a subnet, with MAC, IP, and
  hostname) and DNS record management, and Foreman itself lists them at
  `GET /api/v2/smart_proxies` with their features. That is a view of the network that
  Foreman's *host* records do not contain: leases for machines Foreman does not manage at
  all. It would need its own credential — the smart proxy authenticates by client
  certificate, not by the Foreman user — which is why it is future work rather than another
  toggle here.
- **Coverage-gap reporting for the Linux estate.** The inverse of this import is the more
  valuable report. Because every imported asset is stamped `custom_integration:foreman`,
  the gap is already expressible as a runZero search: a Linux host on a managed subnet that
  Foreman has never heard of has no configuration management, no patching, and no
  provisioning record. A future revision could go further and split the population three
  ways using data already imported — hosts Foreman manages and that report facts, hosts
  Foreman knows about but that have never reported (`last_report` absent), and hosts runZero
  sees that Foreman does not — which is the report a platform team actually acts on.
- **Incremental import.** Foreman's scoped search on hosts supports
  `search=last_report > "1 hour ago"` and `updated_at`, so a scheduled task could fetch only
  hosts changed since the last run. The `search` parameter already exposed here makes this
  configurable by hand today; making it automatic would need the integration to persist the
  previous run's timestamp, which the custom integration framework does not currently offer.
