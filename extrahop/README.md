# Custom Integration: ExtraHop Reveal(x)

## runZero requirements

- Superuser access to the [Custom Integrations configuration](https://console.runzero.com/custom-integrations) in runZero.
- An Explorer with network access to the ExtraHop sensor, RevealX Enterprise console, or the RevealX 360 API endpoint.

## ExtraHop Reveal(x) requirements

- An ExtraHop sensor, a RevealX Enterprise console, or a RevealX 360 console running firmware that exposes the v1 REST API.
- **RevealX Enterprise / sensor:** an API key generated by a user account with read access to devices and networks. The key is sent as `Authorization: ExtraHop apikey=<key>`.
- **RevealX 360:** a set of REST API credentials (an ID and a secret) created on the RevealX 360 API Access page. They are exchanged for a bearer token through `POST /oauth2/token`.
- The credential needs read access to `POST /api/v1/devices/search` and `GET /api/v1/networks`. `GET /api/v1/devices/{id}/software` is only needed if the optional software import is enabled.

## Steps

### ExtraHop configuration

1. **Enable REST API access first.** On both deployment types this is a separate,
   prior step, and skipping it makes the credential impossible to create rather
   than merely unusable. Both require system and access administration privileges.
   - **Sensor or RevealX Enterprise console:** log in to Administration settings
     at `https://<extrahop-hostname>/admin`, and in the **Access Settings**
     section click **API Access**. Under **Manage API Access**, pick either
     *Allow all users to generate an API key* or *Only local users or ExtraHop
     administrators can generate an API key*, then **Save Settings**. The third
     option, *No users can generate an API key*, is a valid hardened state and
     blocks this integration entirely.
   - **RevealX 360:** click the **System Settings** icon, then **All
     Administration**, then **API Access**, and click **Enable** under **Manage
     API Access**. If you have previously disabled and are re-enabling it, the
     REST API can be unavailable for roughly 15 minutes while DNS propagates —
     that gap looks exactly like a broken credential, so wait it out before
     debugging.
2. Choose the privilege level, and read this before defaulting to the obvious one.
   ExtraHop's privilege levels are **System and Access Administration**, **System
   Administration** (RevealX 360 only), **Full Write**, **Limited Write**,
   **Personal Write**, **Full Read-Only**, and **Restricted Read-Only**. The
   name that sounds right for a read-only importer is *Full Read-Only* — but in
   ExtraHop's own capability table, *"Perform all GET operations through the REST
   API"* is listed only against **Limited Write** and **Personal Write**, while
   Full Read-Only and Restricted Read-Only are documented as permitting *"metric
   and record queries"* only. **Personal Write is the least privilege ExtraHop
   explicitly documents as permitting the device calls this integration makes.**
   ExtraHop does not state outright that Full Read-Only is refused, so if you
   want it tighter, try Full Read-Only and verify with the curl in step 4 before
   scheduling anything — a credential that authenticates and then returns
   nothing on the device search is the failure mode to expect. Avoid **System
   and Access Administration**: ExtraHop notes it is similar to full write
   access and can connect sensors and Trace appliances.
3. Generate the credential for your deployment type.
   - **Sensor or RevealX Enterprise console:** in the same **Access Settings >
     API Access** page, use the **Generate an API Key** section — type a
     description, click **Generate**, then scroll to the **API Keys** section and
     copy the key matching that description. Keys are visible only to the user
     who created them or to users with system and access administration
     privileges.
   - **RevealX 360:** on the **API Access** page click **Create Credentials**,
     give it a **Name**, set the **Privileges** field per step 2, set **Packet
     Access** (this integration needs none), and **Save**. Copy the **ID** and
     then the **Secret** from the pane that appears — **the secret cannot be
     viewed or retrieved later**. Read the **API Endpoint** hostname off that
     same page; that hostname, without the `/oauth2/token` suffix, is the URL
     this integration needs. Do not try to construct it from your tenant name —
     ExtraHop publishes no hostname template, so the API Access page is the only
     reliable source.
4. Confirm API access from the Explorer host. For an appliance:
   `curl -H "Authorization: ExtraHop apikey=YOUR_KEY" "https://<host>/api/v1/networks"`.
5. If the appliance uses a private certificate authority, either add the CA to the integration's TLS options or disable TLS validation on the credential.

**On rotation.** RevealX 360 REST API credentials **do not expire on their own
and must be deleted manually to become invalid** — and ExtraHop is explicit that
they are *not* deleted when the user who created them is removed from the
system. A credential minted by a departing administrator keeps working
indefinitely. Track it deliberately; any administrator can delete any
credentials regardless of who created them. Bearer tokens obtained from
`/oauth2/token` are separate and short-lived — valid for 10 minutes — which the
script handles on its own.

### runZero configuration

1. [Create the Custom Integration](https://console.runzero.com/custom-integrations/new).
   - Add a Name and Icon for the integration (e.g., "ExtraHop Reveal(x)").
   - Toggle `Enable custom integration script` to input the finalized script.
   - Click `Validate` to ensure it has valid syntax.
   - Click `Save` to create the Custom Integration.
   - The script embeds its `CONFIG` block, so the credential form is generated automatically with the fields below.
2. [Create the Credential for the Custom Integration](https://console.runzero.com/credentials).
   - Select the type `Custom Integration Script Secrets`.
   - **ExtraHop URL** (`url`): base URL of the sensor, console, or RevealX 360 API endpoint, for example `https://sensor.example.com`.
   - **Deployment type** (`deployment`): `enterprise` for a sensor or RevealX Enterprise console, `reveal360` for the RevealX 360 cloud console. The remaining credential fields are shown based on this choice.
   - **API key** (`api_key`): required for `enterprise`; the API key generated on the appliance.
   - **RevealX 360 client ID** (`client_id`) and **RevealX 360 client secret** (`client_secret`): required for `reveal360`; the ID and secret of the REST API credentials.
   - **Lookback window (days)** (`lookback_days`): optional; only import devices active on the wire within this many days. `0` (the default) imports every device the system has discovered.
   - **Only import devices with an IP address** (`require_ip_address`): optional; default enabled. Disable to also import layer 2 parent devices.
   - **Import observed software** (`include_software`): optional; default disabled. See the note about the per-device request cost below.
   - **Devices per request** (`page_size`): optional; default `1000`.
3. [Create the Custom Integration task](https://console.runzero.com/ingest/custom/).
   - Select the Credential and Custom Integration created in steps 1 and 2.
   - Update the task schedule to recur at the desired timeframes.
   - Select the Explorer you would like the Custom Integration to run from.
   - Click `Save` to kick off the first task.

### Running it from the command line

The runZero Explorer binary runs a script directly, which is the fastest way to see what
an integration would import before scheduling it. `--kwargs` is repeated once per
parameter. For a sensor or RevealX Enterprise console:

```bash
runzero script --filename extrahop/extrahop.star \
  --kwargs url=https://sensor.example.com \
  --kwargs deployment=enterprise \
  --kwargs api_key=exampleFakeApiKey0123456789abcdef \
  --kwargs lookback_days=7 \
  --kwargs page_size=100 \
  --custom-integration-id 1f2e3d4c-5b6a-7988-9a0b-1c2d3e4f5a6b \
  --output ./extrahop-run
```

For RevealX 360, the deployment type changes and the credential is a client ID and
secret rather than an API key:

```bash
runzero script --filename extrahop/extrahop.star \
  --kwargs url=https://example.api.cloud.extrahop.com \
  --kwargs deployment=reveal360 \
  --kwargs client_id=exampleFakeClientId01 \
  --kwargs client_secret=exampleFakeClientSecret0123456789abcdef \
  --kwargs page_size=100 \
  --custom-integration-id 1f2e3d4c-5b6a-7988-9a0b-1c2d3e4f5a6b \
  --output ./extrahop-run
```

`--output` writes the assets the run produced. The scanner refuses to write into a
directory that already exists, so add `--overwrite` when re-running into the same path.
Add `--verbose` for the request-by-request log, or omit `--output` to see only the log
lines. Setting `lookback_days` on a first run bounds the device search to recently
active devices, which keeps a smoke test off a system that has discovered hundreds of
thousands of devices.

`--kwargs` takes the value verbatim as long as the whole argument holds a single `=`, so
a comma inside a value is passed through intact. Only a value that *also* contains an `=`
flips the flag into comma-separated parsing, and then the value is cut at the first comma
— the remainder either becomes a fabricated second parameter or aborts the run with
`must be formatted as key=value`. Nothing here normally carries both, but a
`client_secret` or `api_key` is opaque; if one arrives with an `=` and a comma in it,
wrap the whole argument in a second pair of quotes: `--kwargs '"api_key=ab=cd,ef"'`.

To check the `CONFIG` block and the HTTP and TLS wiring without a live system:

```bash
runzero script --filename extrahop/extrahop.star --validate
```

Validation generates placeholder parameter values and answers from a local dummy server,
so it proves the script initializes, declares its parameters correctly, and issues a
request. It does not prove ExtraHop accepts the credential, that the `deployment` value
matches the system you pointed at, or that any device is parsed. The fixture scenarios
are what exercise the parsing:

```bash
python3 tests/run.py extrahop
```

The same script also runs under the `scan` command, which is what the platform itself
invokes for a scheduled task:

```bash
runzero scan --custom-integration-script-source "$(cat extrahop/extrahop.star)" \
  --custom-integration-id <uuid-from-the-console> \
  --custom-integration-script-kwargs 'url=https://sensor.example.com,deployment=enterprise,api_key=exampleFakeApiKey0123456789abcdef' \
  --output ./extrahop-scan
```

`--custom-integration-id` is the UUID the console shows on the integration's page.
`--custom-integration-entry-function-name` defaults to `main` and only needs setting for
a script with a different entry point. Note that `--custom-integration-script-kwargs`
takes one comma-separated string, so a credential value containing a comma cannot be
passed this way; prefer `script --kwargs` for ad-hoc runs.

### What's next?

- You will see the task kick off on the [tasks](https://console.runzero.com/tasks) page like any other integration.
- The task will update existing assets with data pulled from ExtraHop Reveal(x).
- The task will create new assets when there are no existing assets that meet merge criteria (hostname, MAC, etc).
- You can search for assets enriched by this custom integration with the runZero search `custom_integration:extrahop`.

## Asset identity

- Target entity: a device discovered on the wire by an ExtraHop sensor. ExtraHop is a passive NDR system, so every device record originates from observed traffic rather than from an agent or an inventory import.
- Source ID field: `discovery_id`, scoped by the `appliance_uuid` that owns the record. The appliance UUID is resolved by joining the device's `node_id` to `GET /api/v1/networks`, which returns `{"node_id": ..., "appliance_uuid": ...}` for every connected sensor.
- Documentation evidence:
  - ExtraHop REST API Guide 26.3, *Operand values for device search*: "discovery_id — To search by **the unique ID for the device**, specify the field value as `discovery_id` and the operand value as the discovery ID." This is the only device field the guide describes as *the* unique ID for a device.
  - The same guide describes the numeric `id` as "the unique identifier for the device, **which is displayed as the API ID on the device page**" — an appliance-local handle, not a system-wide one.
  - `GET /api/v1/networks` is documented to return `appliance_uuid` alongside `node_id`, and the device object carries `node_id`. That join is the documented way to attribute a device record to the appliance that produced it.
  - The RevealX UI addresses a device by the pair, not by the discovery ID alone: the device page path is `/extrahop/#/metrics/devices/{appliance_uuid}.{discovery_id}/overview/`. This is the strongest published statement about the uniqueness scope of `discovery_id`, and it is the reason the appliance UUID is part of the runZero ID rather than merely a custom attribute.
  - [Create a custom device](https://docs.extrahop.com/current/create-custom-device/): the Discovery ID "cannot be changed after the custom device is saved", and "the unique Discovery ID for the custom device always remains in the system".
- Uniqueness scope: one appliance (a sensor, or the RevealX 360 tenant's sensor). It is explicitly **not** the numeric `id`. On a console, the same physical device observed by two sensors is returned as two records with two different `id` values and two different `node_id` values; keying on `id` would produce an identity that changes depending on which sensor answered.
- Cardinality: one source row per `(appliance_uuid, discovery_id)` pair. Two cases produce more than one row for one physical device, and both are handled by runZero's network matching rather than by the foreign ID:
  - **Multi-sensor observation.** A device seen by two sensors behind one console yields two records. Because the appliance UUID is part of the ID, these arrive as two foreign IDs. They carry the same wire-observed MAC and IP, so runZero merges them. This is the deliberate trade: scoping by appliance risks a merge that runZero can perform, whereas not scoping risks collapsing two genuinely different devices if `discovery_id` turns out to be appliance-local, which is a corruption runZero cannot undo.
  - **L2 parent and L3 child.** With IP-based discovery enabled, ExtraHop models a layer 3 device as a child of its layer 2 parent via `parent_id`. Both are real device records with their own discovery IDs. The default `require_ip_address` setting applies the documented `ipaddr`/`exists` filter so only addressed devices are imported; disabling it imports the L2 parents too. Note that they will no longer merge into their children by MAC, because an L3 record's inherited `macaddr` is deliberately not emitted as an interface address — see Asset identity.
- Stability: the discovery ID is assigned when the sensor first observes the device and is preserved across polls, renames, role changes, DHCP reassignment, and analysis-level changes. It is not reassigned when the device's MAC, IP, or any of its five names change. Removing the device from the appliance database and re-discovering it produces a new discovery ID.
- Reuse behavior: not documented. ExtraHop publishes no statement about recycling a purged device's discovery ID. This is the one identity property that could not be verified from the public documentation, and it is treated here as non-recycling.
- Presence: `discovery_id` is present on every device object in the documented response schema for `GET /devices`, `POST /devices/search`, and `GET /devices/{id}`. Records that arrive without one, or whose `node_id` cannot be resolved to an appliance UUID, are skipped with a log line rather than given a synthesized ID.
- Final runZero ID: `extrahop:<appliance_uuid>:<discovery_id>`.
- Missing-ID behavior: skip the record. No random or derived fallback is generated. If `GET /api/v1/networks` fails outright, the run stops and imports nothing, because silently substituting a different scope token would re-identify every previously imported asset and duplicate the entire inventory.
- Match behavior (set once in `CONFIG`): `no-ip-break no-name-break`. The discovery ID is authoritative inside its scope, and once it matches, network churn cannot fragment the asset — a foreign-ID match is never disqualified by a conflicting MAC, IP, or hostname, because those checks live only on the MAC, IP, and hostname match paths. These flags therefore govern first contact only, before any ID has matched. `ip-break` and `name-break` are relaxed there because both dimensions are wire-observed and churn: DHCP reassigns the address, and the five name sources appear and disappear with the protocols in use.

  `mac-break` is **kept on**, which is a change from this integration's first release. A layer 3 device inherits `macaddr` from its layer 2 parent, so every host behind one router reports that router's MAC; relaxing `mac-break` let those hosts group together with nothing able to separate them. The address is now suppressed for L3 records (kept as the `extrahop_macaddr` attribute), so any MAC that reaches an interface is genuinely that device's own and a conflict is real evidence worth acting on.
- Verdict: **scoped authoritative**.

### Notes

- **What is imported.** Assets from `POST /api/v1/devices/search`. The appliance UUID map comes from `GET /api/v1/networks`. Optionally, software from `GET /api/v1/devices/{id}/software`.
- **Names.** ExtraHop learns device names from five independent wire sources, and any subset can be populated for one device. `dns_name`, `netbios_name`, `dhcp_name`, and `cdp_name` are imported as hostnames, along with the operator-set `custom_name`. `display_name` is imported only when it differs from `default_name`, because it mirrors `default_name` unless somebody has renamed the device, and `default_name` is a synthesized vendor-plus-MAC label ("VMware 83B4FB") rather than an observed name. Both are kept as custom attributes in all cases.
- **Network interfaces.** `macaddr` plus `ipaddr4` and `ipaddr6` form a single interface. Because ExtraHop observes these on the wire rather than reading them from an agent, the MAC/IP fidelity is high and they are the primary merge signal for this integration.
- **Device type.** Derived from `role`, falling back to `auto_role`. The mapping table uses the documented `custom_type` enum from `PATCH /devices/{id}`, which is the same vocabulary the read-only role fields use. ExtraHop's explicit "unclassified" token `other` is not mapped, so no device type is asserted that the sensor did not observe. Unlisted role tokens are passed through with underscores expanded. `device_class` (values such as `node` and `gateway`) is an internal ExtraHop classification rather than a device type and is kept as a custom attribute.
- **Timestamps.** `discover_time` becomes `firstSeenTS`. `last_seen_time` becomes `lastSeenTS`, falling back to `mod_time` when it is absent. Both are documented as milliseconds since the epoch. Note that the published response schema types `last_seen_time` as a string while vendor-recorded samples show a number; the integration accepts either form and ignores zero.
- **Pagination.** `POST /api/v1/devices/search` accepts `limit` and `offset` in the request body, both documented in the REST API Guide, and ExtraHop's own reference script [`extract_device_list.py`](https://github.com/ExtraHop/code-examples/blob/main/extract_device_list/extract_device_list.py) pages exactly this way: post `{"limit": N, "offset": k}`, walk the offset forward, and stop when a page comes back empty. This integration does the same and additionally stops when a page returns fewer than `page_size` records.
  - Time-window slicing over `active_from`/`active_until` is **not** required and is not used. Those two fields are used only to express the optional lookback window.
  - No sort order is documented for the endpoint, so an inventory that changes mid-walk can in principle surface the same device in two pages or skip one. Duplicates are eliminated by tracking the `(appliance_uuid, discovery_id)` pairs already reported during the run; only those key strings are retained between pages, never the device records. A skip caused by a device being discovered mid-run is corrected on the next poll.
  - `POST /devices/search` has no documented ceiling on `limit + offset`. The 10,000 cap called out in the guide applies to the records search, not to devices.
- **Lookback.** `lookback_days` is sent as a negative `active_from`, which the API evaluates relative to the current time in milliseconds. With `lookback_days = 0` the body sends `active_from: 1` and `active_until: 0`, which is ExtraHop's documented recipe for "every device the system has discovered".
- **Software.** Disabled by default. `GET /api/v1/devices/{id}/software` is a per-device sub-resource, so enabling it issues one additional request for every imported device; on an estate of tens of thousands of devices that is not appropriate for a routine poll. ExtraHop publishes no CPE for observed software, so `Software.cpe23` is never set.
- **No services.** ExtraHop knows which protocols a device speaks (the `activity` array and the role labels), but neither the device object nor a cheap companion call exposes a listening port and transport. Port numbers are not synthesized from activity labels, so no `Service` objects are emitted. The activity labels are preserved as a custom attribute.
- **No vulnerabilities.** ExtraHop detections are behavioral findings, not CVEs, and are deliberately not mapped to `Vulnerability` objects. See `## Future`.
- **Rate limiting.** ExtraHop does not publish a REST API rate limit. Requests use the shared HTTP helper with a retry budget of 3 and exponential backoff, which covers 408/425/429 and 5xx responses and honors `Retry-After`.
- **RevealX 360 token lifetime.** The token returned by `POST /oauth2/token` is fetched once per run and its `expires_in` (typically one hour) is not tracked. A single run against an unusually large estate could in principle outlive the token; the integration does not currently re-authenticate mid-run. This has not been observed and is not handled.
- **Unverified assumptions.** Whether `discovery_id` is unique across sensors or only within one appliance is not stated in the public documentation; the appliance-scoped reading is taken because it is the safer failure mode and because the RevealX UI addresses devices by the pair. Whether ExtraHop recycles a purged device's discovery ID is likewise undocumented.
- This integration was validated against local fixtures, not a live ExtraHop tenant.

## Future

- **Detection ingestion** via `POST /api/v1/detections/search`, with `GET /api/v1/detections/{id}` for detail. ExtraHop detections are *behavioral* findings — a device performing a port scan, exfiltrating data over DNS, or exhibiting lateral-movement patterns — produced by machine learning over wire data. They are not vulnerabilities: they carry no CVE, no CPE, no CVSS vector, and no notion of a patch that resolves them. Mapping them onto `Vulnerability` objects would put a fundamentally different data class into a field that runZero users read as "this asset has an unpatched flaw", and the two would then be indistinguishable in search and reporting. If detections are ingested in a future version, the honest home for them is a separate finding type or a set of custom attributes and tags (detection category, risk score, participant role as offender or victim), not the vulnerability model. `PATCH /api/v1/detections/{id}` would additionally allow runZero to write triage state back.
- **Device tagging as an outbound integration** via `GET /api/v1/tags`, `POST /api/v1/tags`, and `POST /api/v1/tags/{id}/devices`. Pushing runZero's own classifications — device type, ownership, site, or "unmanaged" status — onto ExtraHop devices as tags is a clean, non-destructive write: tags are additive metadata, the assignment endpoint takes explicit `assign` and `unassign` arrays, and nothing about the device record itself is modified. The join key is the numeric device `id`, which this integration already records as `extrahop_device_id`.
- **Watchlist management as an outbound integration** via `GET /api/v1/watchlist/devices` and `POST /api/v1/watchlist/devices`. The watchlist forces a device into Advanced Analysis, ExtraHop's most detailed telemetry tier, and capacity for it is finite. runZero is well placed to decide what belongs there: assets it has flagged as high-risk, newly discovered unmanaged devices, or assets running end-of-life software could be promoted onto the watchlist automatically, and demoted when they are remediated. The current integration already imports `on_watchlist` so the existing state is visible in runZero first.
- **Peer relationships from activity maps** via `POST /api/v1/activitymaps/query`. ExtraHop records who talks to whom, over which protocol, in which direction. That is a genuine relationship graph, not asset attributes, and runZero has no inbound relationship import today. When one exists, this is a strong source for it — communication topology observed on the wire is exactly the data that turns an asset inventory into a network model.
- **NDR coverage-gap reporting.** This is the strongest pairing of the two products and needs no new API surface. runZero discovers assets actively, from the outside in; ExtraHop discovers them passively, from the wire. An asset runZero scans that ExtraHop has never seen is, by definition, on a network segment the sensors are not watching — a monitoring blind spot, not a missing asset. Inverting the comparison finds the opposite gap: devices ExtraHop observes that runZero has never scanned, meaning they sit outside the configured scan scope. Because both sides key on wire-observed MAC and IP, the join is reliable. A future version could emit the ExtraHop-visible set as a distinguishable tag so the difference is a saved query rather than a manual export.
- **Alert rules** via `GET /api/v1/alerts` are configuration objects (thresholds and detection rules), not per-asset findings, so they are not a candidate for asset enrichment. `POST /api/v1/alerts` would allow runZero to provision alert rules, but that is a configuration-management use case rather than an asset one.
- The API exposes no serial number, no operating system, and no firmware version for a device. That is inherent to passive discovery rather than a gap in the integration: ExtraHop reports what it can infer from traffic, and those attributes are not on the wire. runZero should not expect this source to contribute them.

## API documentation

- [ExtraHop REST API Guide](https://docs.extrahop.com/current/rest-api-guide/) — device resource, `POST /devices/search` body (`limit`, `offset`, `active_from`, `active_until`, `filter`), device object schema, `GET /networks`, `GET /devices/{id}/software`, and the `ExtraHop apikey=` authentication header. Also available as a [PDF](https://docs.extrahop.com/current/rest-api-guide/rest-api-guide.pdf).
- [RevealX 360 REST API Guide](https://docs.extrahop.com/current/rx360-rest-api/) — the cloud console's equivalent endpoints and the `POST /oauth2/token` client-credentials flow with HTTP Basic client authentication.
- [Extract the device list through the REST API](https://docs.extrahop.com/current/rest-extract-devices/) — the documented `active_from: 1, active_until: 0` full-inventory recipe and the RevealX 360 token exchange, both shown for `POST /api/v1/devices/search`.
- [Search for a device through the REST API](https://docs.extrahop.com/current/rest-search-for-device/) — filter object structure and the `discovery_id` search field.
- [ExtraHop `extract_device_list.py` reference script](https://github.com/ExtraHop/code-examples/blob/main/extract_device_list/extract_device_list.py) — the vendor's own `limit`/`offset` pagination loop over `POST /api/v1/devices/search`, and the L2-parent filtering behavior.
- [Create a custom device](https://docs.extrahop.com/current/create-custom-device/) — Discovery ID immutability and persistence.
- [Device Discovery FAQ](https://docs.extrahop.com/current/device-disc-faq/) — device activity and inactivity semantics behind `active_from`/`active_until`.
