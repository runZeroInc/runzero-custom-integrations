# Custom Integration: Bitsight

Import assets and associated findings/vulnerabilities by Company ID.

## Getting Started

- Clone this repository

```
git clone https://github.com/runZeroInc/runzero-custom-integrations.git
``` 

## runZero requirements

- Superuser access to the [Custom Integrations configuration](https://console.runzero.com/custom-integrations) in runZero
- An Explorer with outbound HTTPS access to `https://api.bitsighttech.com`

##  Bitsight requirements

- A Bitsight account with API access, and the **company GUID** of the organization whose assets you want to import.
- A Bitsight **API token**. Authentication is HTTP Basic with the token as the **username** and an **empty password** — Bitsight's own examples use `-u api_token:` with the trailing colon, and that is exactly what this integration sends.
- Bitsight issues two kinds of token, and they are not equivalent:
  - A **User API Token**, generated by any user for themselves.
  - A **Company API Token**, which only an Admin or VRM Admin can generate.

  Bitsight's `GET: Assets` documentation is written around the company token. Whether a *user* token is accepted on `/ratings/v1/companies/{guid}/assets` is **not stated either way in the vendor documentation**, so it is worth testing a user token first — it is the lower-privilege option — and falling back to a company token if the call is refused. This README does not claim to know which one your tenant requires.
- Some `GET: Assets` query parameters (`country_code`, `hosted_by`, `services`, `products`, `threats`) require an **Attack Surface Analytics** subscription. This integration does not send any of them, so it does not depend on that subscription. Whether base asset access requires a particular Security Performance Management tier is **not something we could confirm from Bitsight's documentation**; if the assets endpoint returns 403 with a valid token, that is the question to put to your Bitsight account team.

## Steps

### Bitsight configuration

1. **Generate the API token.** In the Bitsight portal, go to **Settings > Account > User Preferences**.
   - For a **User API Token**, use **Generate New Token** in the User API Token section. The value stays visible on that page afterwards, so you can come back for it. Generating a new one **replaces and invalidates** the previous token, so do not regenerate a token another integration is using.
   - For a **Company API Token**, enter a description in the **New Token** field of the Company API Token section and click **Generate**. This one is **displayed only once**. Only Admin and VRM Admin roles can create it.
   - Bitsight documents no expiry for either token type.

2. **Find your company GUID.** This is the `company_id` parameter, and it is a GUID rather than a name. The reliable way to read it is the portfolio endpoint, which returns your own organization under `summaries.my-company`:

   ```bash
   curl -s -u '<api_token>:' \
     https://api.bitsighttech.com/ratings/v2/portfolio | jq '.summaries."my-company"'
   ```

   Note the trailing colon after the token — that is the empty password, and omitting it will prompt for one.

   `GET /ratings/v1/companies/{guid}` cannot be used to *discover* the GUID, because it requires the GUID as input. We could not confirm from Bitsight's documentation that any portal page displays the GUID directly, so the API call above is the step this README can stand behind.

3. **Confirm the token and GUID together** before configuring anything in runZero:

   ```bash
   curl -s -u '<api_token>:' \
     'https://api.bitsighttech.com/ratings/v1/companies/<company_guid>/assets?is_ip=true&limit=1' | jq .
   ```

   A working pair returns `{"links": {...}, "count": N, "results": [...]}`. A 401 is the token; a 403 is permissions or subscription; a 404 is usually the wrong GUID.

4. **Leave the API URL alone unless you have been told otherwise.** The `url` parameter defaults to `https://api.bitsighttech.com` and should only be changed for a regional or self-hosted deployment.

### runZero configuration

1. (OPTIONAL) - make any neccessary changes to the script to align with your environment. 
    - Modify API calls as needed to filter assets
      - Bitsight classifies a few asset types (IP, CIDR, Domain). The default behavior of the script is to import only IP-based assets, by sending `is_ip=true` on the assets request, as these are easily merged with existing assets. In testing it also appeared that many domain-based assets are subdomains belonging to IP-based assets, ultimately, creating duplicates of little value. To import all asset types, comment out the `params = {'is_ip': 'true'}` line in `get_assets` and uncomment the empty `params = {}` line directly below it.
    - Modify datapoints uploaded to runZero as needed 
2. [Create the Credential for the Custom Integration](https://console.runzero.com/credentials)
    - Select the type `Custom Integration Script Secrets`
    - Both `company_id` and `api_token` are required
    - `company_id` corresponds to the Bitsight company GUID found in step 2 above
    - `api_token` corresponds to the User or Company API token created in Bitsight
    - `url` is optional and defaults to `https://api.bitsighttech.com`
3. [Create the Custom Integration](https://console.runzero.com/custom-integrations/new)
    - Add a Name and Icon 
    - Toggle `Enable custom integration script` to input your finalized script
    - Make any modifications to the script for the desired output.
    - Click `Validate` to ensure it has valid syntax
    - Click `Save` to create the Custom Integration 
4. [Create the Custom Integration task](https://console.runzero.com/ingest/custom/)
    - Select the Credential and Custom Integration created in steps 2 and 3
    - Update the task schedule to recur at the desired timeframes
    - Select the Explorer you'd like the Custom Integration to run from
    - Click `Save` to kick off the first task

### Running it from the command line

The runZero Explorer binary runs a script directly, which is the fastest way to
confirm a token and GUID pair and see what Bitsight actually returns before
scheduling anything. `--kwargs` is repeated once per parameter:

```bash
runzero script --filename bitsight/bitsight.star \
  --kwargs url=https://api.bitsighttech.com \
  --kwargs company_id=a1b2c3d4-e5f6-4071-89ab-cdef01234567 \
  --kwargs api_token=7f3a91c4e0b84d26a5c8f1e7d09b3a42b6d40f9a \
  --custom-integration-id 1f2e3d4c-5b6a-7988-9a0b-1c2d3e4f5a6b \
  --output ./bitsight-run
```

`--output` writes the assets the run produced, and `--overwrite` replaces a
directory from a previous run — the scanner refuses an `--output` directory that
already exists otherwise. Add `--verbose` for the request-by-request log. Omit
`--output` to see only the log lines.

There are only three parameters here, so this integration has no cheap "small
first run" switch — no page size, no cap, no lookback. **The cost is in the
findings.** After collecting the asset list, the script issues one findings
request *per asset*, so a company with a large external footprint produces a
long run and there is no parameter to limit it. Budget accordingly, and prefer
running the first test against a subsidiary GUID if you have one.

This is also the place to settle the **user token versus company token**
question described above. Run it with a user token; if the assets request comes
back 403 while the same token works against `/ratings/v2/portfolio`, you need a
company token.

`--kwargs` takes the value verbatim as long as the whole argument holds a single
`=`, so a comma inside a value is passed through intact. Only a value that
*also* contains an `=` flips the flag into comma-separated parsing, and then the
value is cut at the first comma — the remainder either becomes a fabricated
second parameter or aborts the run with `must be formatted as key=value`. A
Bitsight token and a company GUID contain neither character, so this is not a
practical problem for this integration.

To check the `CONFIG` block and the HTTP and TLS wiring without a live server:

```bash
runzero script --filename bitsight/bitsight.star --validate
```

Validation generates placeholder parameter values and answers from a local
dummy server, so it proves the script initializes, declares its parameters
correctly, and issues a request. It does not prove Bitsight accepts the Basic
credential, that the GUID resolves, or that any asset is parsed.

The fixtures under `bitsight/tests/fixtures/` exercise the parsing, both cursor
walks, and the timestamp handling offline:

```bash
python3 tests/run.py bitsight
```

The same script also runs under the `scan` command, which is what the platform
itself invokes for a scheduled task:

```bash
runzero scan --custom-integration-script-source "$(cat bitsight/bitsight.star)" \
  --custom-integration-id <uuid-from-the-console> \
  --custom-integration-script-kwargs 'company_id=a1b2c3d4-e5f6-4071-89ab-cdef01234567,api_token=<token>' \
  --output ./bitsight-scan
```

`--custom-integration-id` is the UUID the console shows on the integration's
page. `--custom-integration-entry-function-name` defaults to `main`. Note that
`--custom-integration-script-kwargs` takes one comma-separated string, so a
value containing a comma cannot be passed this way; prefer `script --kwargs`
for ad-hoc runs.

### What's next?

- You will see the task kick off on the [tasks](https://console.runzero.com/tasks) page like any other integration 
- The task will update the existing assets with the data pulled from the Custom Integration source 
- The task will create new assets for when there are no existing assets that meet merge criteria (hostname, MAC, etc)
- You can search for assets enriched by this custom integration with the runZero search `custom_integration:bitsight`

## Asset identity

- Target entity: an **entry in a company's Bitsight attack surface** — an IP address by default, and optionally a domain or a CIDR block when the `is_ip` filter is removed. Note the consequence of that last case: a CIDR is a *range*, not a host, so relaxing the filter imports records that do not describe a single machine at all.
- Source ID field: **none exists.** `GET /ratings/v1/companies/{guid}/assets` publishes no opaque per-asset key — the identifying field is `asset`, which is literally the IP address or domain name, alongside `asset_type`. The script therefore composes one: `bitsight:{asset_type or "unknown"}:{asset}`, for example `bitsight:ip:203.0.113.10`. A record with no `asset` value is skipped with `bitsight: skipping record with no asset field`.
- Uniqueness scope: the company GUID the credential is pointed at. The composed id does **not** include that GUID, so importing two Bitsight companies through the same custom integration puts them in one id space — and because the id is the address itself, two companies that share an address (a common CDN or hosting range) collide on it directly.
- Cardinality: one source row per asset. Findings are fetched separately, one request per asset, and attach to that asset as vulnerabilities rather than becoming assets of their own.
- Stability: **the id is only as stable as the address.** It changes whenever Bitsight reclassifies the record (`asset_type` is part of the composed value) and it points at whatever host holds that address today. This is not a persistent identifier for a machine and was never going to be — Bitsight is an outside-in ratings service that observes an address from the internet, not an agent or an inventory system with a device key.
- Reuse behavior: **guaranteed, by construction.** An IP address handed back to a cloud provider and reissued to an unrelated tenant produces the same composed id for a completely different machine.
- Presence: `asset` is present on every documented record; the skip path exists for malformed rows.
- Final runZero ID: `bitsight:<asset_type>:<asset>`, e.g. `bitsight:ip:203.0.113.10` or `bitsight:domain:www.example.com`.
- Missing-ID behavior: skip and log. No identifier is synthesized from anything else.
- Match behavior (set once in `CONFIG`): **`no-id-match no-id-break`** — declared once at the top level of `CONFIG`, not per record.
- Verdict: **not authoritative, and correctly declared as such.**

This is the textbook case for the relaxed setting and the code gets it right. Because the identifier *is* an address, using it to find merge candidates would merge whatever machine holds that address today onto whatever held it when Bitsight last observed it — and once a foreign-id match is made, nothing can veto it: a conflicting MAC, IP, or hostname does not disqualify a match that was found by foreign id. `no-id-match` prevents the match from ever being attempted, and `no-id-break` stops the composed value from disqualifying a legitimate merge found some other way. Correlation is left to the address and hostname carried on the record, which is the right signal for outside-in data.

One consequence to expect when reading the results: on the default `is_ip=true` path the record's `asset` value is an IP address, and it is imported **both** as the network interface address and as the asset's hostname, because Bitsight publishes no separate name field. Assets from this source will therefore show an IP-shaped hostname. That is faithful to what Bitsight returns rather than a defect in the mapping, but it is worth knowing before writing a search against it.

## Future

- **Portfolio-wide import instead of one company at a time.** `company_id` is a single required GUID, so one credential imports one company. `GET /ratings/v2/portfolio` — already used in this README to *discover* your own GUID — returns every company in the portfolio, which is the natural loop for an MSSP or a parent organization tracking subsidiaries. The identity work above is the blocker rather than the API: the composed id contains no company GUID, so a portfolio walk would need to add one before two companies could safely coexist in a single runZero organization.
- **Findings are already imported, but the request pattern is the limiting factor.** `GET /ratings/v1/companies/{guid}/findings` is called **once per asset**, with `assets.asset=<address>`, which is why this integration has no cheap small first run. The same endpoint accepts a `first_seen`/`last_seen` window and severity filters, so an incremental mode — fetch the whole company's findings once, filtered to what changed since the last run, and group them by address locally — would replace N requests with a handful. That is the single highest-value change available here.
- **Vulnerability enrichment this integration deliberately leaves on the floor.** Bitsight findings carry `risk_vector` and `risk_category` (which risk area the finding belongs to: patching cadence, TLS configuration, open ports, botnet infections), `remediation` guidance, and `evidence_key`. Those already land as vulnerability custom attributes. What is *not* imported is the vulnerability-specific detail Bitsight publishes for its own vulnerability risk vectors — the CVE-bearing findings — which currently arrive with `id` and `name` set to the finding's `details.diligence_annotations.message` string rather than to a CVE identifier. A findings record whose annotations name a CVE should populate the `Vulnerability.cve` field so runZero's own vulnerability reporting can use it; today it does not.
- **Service data from an outside-in view.** Bitsight observes listening services from the internet and reports `dest_port` and `transport` on findings, which this integration already reads to bind a finding to a port. The same data would support emitting `Service` records, giving runZero an internet-facing port list for addresses its own scanners may not be positioned to reach. The caveat is that Bitsight's view is historical and inferred, not a live scan, so those services should be marked as observed-by-a-third-party rather than presented as current.
- **Coverage-gap reporting in both directions, and this is the direction Bitsight is uniquely good at.** Bitsight's whole product is finding assets attributed to your company *from the outside* — including shadow IT and forgotten cloud footprint that no internal scanner is pointed at. Diffing Bitsight's asset list against runZero's inventory therefore surfaces genuinely unknown external attack surface, which is a different and more valuable finding than the usual agent-coverage gap. The reverse diff (runZero assets Bitsight has never observed) mostly identifies internal-only hosts and is less interesting.
- **Attribution correction is a write path that does not exist.** A recurring operational problem with outside-in ratings is a misattributed address — an IP that Bitsight assigns to your company but that you do not own. Bitsight handles those disputes through its portal workflow, and **no public API for submitting or resolving an attribution dispute could be identified**, so there is no way to close that loop from runZero. Stated here rather than left as an open possibility.
- **A subscription boundary limits several of the above.** The `country_code`, `hosted_by`, `services`, `products`, and `threats` query parameters require an Attack Surface Analytics subscription. This integration sends none of them, which is why it works without one — but any enrichment built on those fields inherits that requirement, and the `cloud_context`, `hosted_by`, and `products` attributes it currently imports will simply be absent on tenants without it.

### Fixed defects

Three behaviors have been corrected. They are recorded because each changed what a run produced, and because the first two were invisible in the log — a run affected by either looked successful.

- **Both paging loops re-sent their filter parameters on the cursor URL.** `get_assets` and `get_findings` followed Bitsight's `links.next` absolute URL but also passed `params=` on every request. The HTTP helper's `params` argument *replaces* a URL's query string rather than merging with it, so the cursor's own offset was discarded and each iteration re-fetched the first page. It still terminated, by counting rows against `count`, but it did so by accumulating the same page repeatedly — duplicated assets and duplicated findings, reported as a clean run. The cursor is now followed verbatim with no parameters, and `count` is a backstop rather than the loop driver. That last part also fixes a quieter bug in the same condition: the bound was `len(...) < count - 1`, which stopped one row short of the reported total and dropped the final page.
- **A finding with an unusable `first_seen` value ended the run.** `build_vuln` called `parse_time(first_seen)` unconditionally after its reformatting step, and `parse_time` has no recoverable failure mode in Starlark — it aborts the script rather than returning an error, taking every asset and finding already built with it. An absent or null `first_seen` reached it as `None`; a value that is not a date at all, or a space-separated timestamp, survived the reformatting step and reached it as nonsense. The value is now screened against an RFC 3339 pattern, and a finding that fails the screen is imported without a `firstDetectedTS` rather than ending the run.
- **The `country` custom attribute was always empty.** It was read from `asset.get('coutry')`, a misspelling, so the value never arrived even though Bitsight returns it on every asset. `countryCode` was read correctly and was unaffected.

All three are covered offline: `paged` walks a two-page asset cursor with a two-page findings cursor behind it and asserts the exact request count, `unparseable-first-seen` feeds five findings of which four used to abort the run, and `happy` asserts the `country` attribute now arrives.
